# Tasks

## 1. backend: storage and client API

- [ ] 1.1 Add the `messages` table (see design.md "Message storage"): UUIDv7 id, `account_id`, `assistant_id` with a composite foreign key to `assistants` and `ON DELETE CASCADE`, nullable `link_id`, `sender`, `text`, nullable `status`, nullable `client_id` (unique per account for the user's messages, per `link_id` for the Assistant's), `inserted_at`, and an index on `(assistant_id, id)`; verify migrate and rollback succeed and a test shows deleting an account deletes its messages and a message cannot point at another account's Assistant
- [ ] 1.2 Implement text validation (1–4,000 Unicode code points, not only Unicode White_Space characters, no trimming) shared by the client API and ALP; verify with unit tests for empty, whitespace-only (including non-ASCII spaces), 4,000, 4,001, multi-byte and emoji characters, and line breaks, using the shared test vectors also used by `al` and the app
- [ ] 1.3 Implement `GET /api/v1/assistants/:id/messages` (`limit` default 50, max 100, `before`, oldest first, `has_more`) and add `latest_message` to the Assistants list; verify with tests for paging across 120 messages, `before`, an empty Assistant, and `404` for another account's Assistant
- [ ] 1.4 Implement `POST /api/v1/assistants/:id/messages` (`client_id`, `text`): insert as `sending`, run the delivery attempt (group 2) in a supervised `Task`, respond `201` with the final message, store a message for an Assistant with no online Assistant Link (or none at all) as `failed` at once, and answer a repeated `client_id` with `200`: for a `failed` message move it back to `sending` with a compare-and-set update and attempt again with the same id and place, for `sending` or `sent` return it without an attempt; include `client_id` in the message object; verify with tests for `sent`, `failed`, no Assistant Link, invalid text (`422`), re-post of a sent and a sending message, two concurrent re-posts of a failed one (one attempt), and that the final status is written even when the request process is killed mid-attempt
- [ ] 1.5 Mark `sending` messages older than the 10 second deadline as `failed` on service start and periodically, and make the delivery Task stop quietly when its message or account was deleted; verify with tests that a stale `sending` message becomes `failed` after a restart and that deleting the account mid-attempt raises no error

## 2. backend: ALP

- [ ] 2.1 Add the pid and open time of each agent connection to its Presence metadata, and implement delivery: pick the first online Link in creation order, send `message.deliver` to its newest connection, fall back to the next on an error response or a closing connection, never to two at once, and fail after 10 seconds in total or at once when no Link is online; the connection process matches the response `id` to the waiting task and ignores a response with an unknown or expired `id` without closing the connection; verify with tests for receipt, error, `-32601`, `-32001`, silence (short timeout), an unknown response `id`, two Assistant Links, two connections, and a connection closing mid-attempt
- [ ] 2.2 Implement `POST /alp/v1/messages` with Link token auth: store the message from the Link's Assistant, respond `201 {message_id, sent_at}`, accept an optional `client_id` (unique per Assistant Link; a repeat returns `200` with the stored message and stores nothing), return `422` `text_empty`, `text_too_long`, `invalid_params`, and `401 unauthorized`; it must not touch presence or `last_active_at`; verify with tests for each response, a repeated `client_id`, and that an offline Assistant Link stays offline with an unchanged last active time
- [ ] 2.3 Send `message.created` on the app's live connection for each message from the Assistant, through the account's PubSub topic; verify with a test that an app connection receives it within 2 seconds of the agent's `POST`, and that another account's connection does not
- [ ] 2.4 Update `docs/alp/v1.md`: add `message.deliver` (params, result, `-32601` and `-32001` `not_received` meanings, at-least-once note, the stable `message_id`, and that readers dedupe by it) under "Methods" and say that the service now sends a request where it needs a receipt and accepts the agent's responses; add `POST /alp/v1/messages` (with `client_id`) and the `text_empty` and `text_too_long` rows to the HTTP error table; add the text rules (4,000 Unicode code points, Unicode White_Space), the connection choice rule (which connection receives a message), and a short example session using `curl`; verify every example in the document against a running service
- [ ] 2.5 Update the agent `install.md` in the backend repository to show how an agent reads `al wait` events (its standard output must be read, or messages fail with `not_received`) and replies with `al send`; verify an agent following it can receive and answer a message

## 3. cli

- [ ] 3.2 Implement `al send <text>` and `al send -` (standard input, one trailing line feed dropped): `POST /alp/v1/messages` with the Link key, print `{"message_id", "sent_at"}` or `{"error": {"code", "message"}}` (text for `--human`), exit 0/2/3/4/5 as in the spec, never open an agent connection; verify with tests against a mock HTTP server for an argument, standard input, a missing text (exit 2), no key (3), `text_too_long` and `unauthorized` (4), and an unreachable server (5); `al` does not send `client_id`, and it passes the shared text test vectors to the service unchanged
- [ ] 3.3 Update `cli/README.md` with `al send`, the event format on `al wait`'s standard output (`type`, readers ignore unknown fields and types), the receipt timing, and exit code 4's wider meaning; verify every documented command runs as written against a local service
