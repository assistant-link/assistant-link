# Tasks

## 1. backend: storage and client API

- [ ] 1.1 Add the `messages` table (see design.md "Message storage"): UUIDv7 id, `account_id`, `assistant_id` with a composite foreign key to `assistants` and `ON DELETE CASCADE`, nullable `seq`, `sender`, `text`, nullable `status` (`sent`, `delivered`, `expired`), nullable `client_id` (unique per account for the user's messages, per `link_id` for the Assistant's), nullable `link_id`, `inserted_at`, and indexes on `(assistant_id, id)` and `(assistant_id, seq)`; add `assistants.last_message_seq` (bigint, default 0) and `assistant_links.delivered_through` (bigint, set at pairing, 0 for existing Links) and the delivery retention setting (default 7 days); verify migrate and rollback succeed and a test shows deleting an account deletes its messages and cursors and a message cannot point at another account's Assistant
- [ ] 1.2 Implement text validation (1–4,000 Unicode code points, not only Unicode White_Space characters, no trimming) shared by the client API and ALP; verify with unit tests for empty, whitespace-only (including non-ASCII spaces), 4,000, 4,001, multi-byte and emoji characters, and line breaks, using the shared test vectors also used by `al` and the app
- [ ] 1.3 Implement `GET /api/v1/assistants/:id/messages` (`limit` default 50, max 100, `before`, oldest first, `has_more`) and add `latest_message` to the Assistants list; verify with tests for paging across 120 messages, `before`, an empty Assistant, a message older than the retention still listed, and `404` for another account's Assistant
- [ ] 1.4 Implement `POST /api/v1/assistants/:id/messages` (`client_id`, `text`): in one transaction assign `seq` with `UPDATE assistants SET last_message_seq = last_message_seq + 1 … RETURNING` and store the message as `sent`, then broadcast "message stored" on PubSub after commit, and respond `201` with it at once, whether or not any Assistant Link is online; answer a repeated `client_id` with `200` and the stored message in its current state without storing or delivering anything, and `409 client_id_conflict` when its text or Assistant differs; include `client_id` and `status` in the message object; verify with tests for a stored message with every Assistant Link offline, invalid text (`422`), a repeated `client_id` of a `sent`, a `delivered`, and an `expired` message, a conflicting `client_id` (`409`), `404`, and two concurrent stores whose commits finish in the reverse order of their start (`seq` follows commit order and neither is skipped by a cursor)
- [ ] 1.5 Implement the status changes: `sent` or `expired` to `delivered` on the first acknowledgement (conditional update, once) and `sent` to `expired` by a periodic job for messages older than the retention, run on one node only under a Postgres advisory lock, each sending `message.updated` on the app's live connection through the account's PubSub topic; verify with tests that the app connection receives `message.updated` within 2 seconds of an acknowledgement and of an expiry (retention set to a few seconds), that a second Link's acknowledgement sends nothing, that another account's connection receives nothing, that a lagging job does not break delivery, that an acknowledgement arriving after the job expired the message makes it `delivered` and sends `message.updated`, and that with the lock held elsewhere the job does nothing
- [ ] 1.6 Send `message.created` on the app's live connection for each message from the Assistant; verify with a test that an app connection receives it within 2 seconds of the agent's `POST`, and that another account's connection does not

## 2. backend: ALP and delivery

- [ ] 2.1 Add the pid and open time of each agent connection to its Presence metadata, and implement the per-Link delivery process (design.md "The cursor"), registered under a `:global` name keyed by `link_id` and woken by the PubSub "message stored" notice: started with the Link's first connection and stopped with its last, it reads the next event with `seq` after `delivered_through` within the retention, sends `event.deliver` (request `id` = event `id`) to the newest connection, falls back to the next-newest on an error, a close, or 30 seconds without a response, waits 30 seconds when every connection failed a round, doubling up to 5 minutes, restarts at once and resets the wait on a new connection, never sends to two at once, and advances the cursor only on the result with the monotonic update `WHERE delivered_through < $seq`; a late response for the event in flight is accepted as its acknowledgement and cancels the retry, and a response for any other `id` is ignored without closing; verify with tests for acknowledgement, error, `-32601`, `-32001`, silence (short timeout), a late response for the event in flight, a response with an unknown `id`, two connections of one Link, the backoff (30 s, 60 s, … capped at 5 minutes, reset by a new connection), a late or duplicate acknowledgement that does not move the cursor back, and a message stored while the delivery process is starting
- [ ] 2.2 In the pairing transaction set the cursor to the Assistant's current `last_message_seq`, and trigger delivery to every Link of the Assistant when a message is stored; verify with tests for: a Link receiving nothing sent before its pairing and every message stored after it (including one stored in a transaction that commits after the pairing), two Links each receiving every message, a slow Link not holding back the other, and a message sent while a Link is offline arriving after it connects
- [ ] 2.3 Verify catch-up and cursor behavior end to end in the service: catch-up in order after a reconnect, resume after the last acknowledged event with no repeat, independent cursors of two Links, redelivery with the same `id` after a lost acknowledgement (connection closed before the response), no delivery of a message older than the retention (retention set to a few seconds), and a restart of the delivery process resuming from the stored cursor
- [ ] 2.4 Implement `POST /alp/v1/messages` with Link token auth: store the message from the Link's Assistant, respond `201 {message_id, sent_at}`, accept an optional `client_id` (unique per Link; a repeat answers `200` with the stored message and stores nothing; a different text is `409 client_id_conflict`), return `422` `text_empty`, `text_too_long`, `invalid_params`, and `401 unauthorized`; it must not touch presence or `last_active_at`, and must not create an event for other Links; verify with tests for each response, a repeated and a conflicting `client_id`, that an offline Assistant Link stays offline with an unchanged last active time, and that another Link of the Assistant receives no event
- [ ] 2.5 Update `docs/alp/v1.md`: add `event.deliver` (params are the event, `message` as the first type, result, `-32601` and `-32001` `not_received` meanings, one request at a time and in order, the service-side cursor and catch-up, at-least-once with the stable `id` readers dedupe by, and that later types add `type` values) under "Methods" and say that the service now sends a request where it needs an acknowledgement and accepts the agent's responses; say that only `id` and `type` are required on every event; add `POST /alp/v1/messages` with the optional `client_id` and the `text_empty`, `text_too_long`, and `client_id_conflict` rows to the HTTP error table; add the text rules, the delivery retention (7 days), the rule for several connections with the backoff, and a short example session using `curl`; verify every example in the document against a running service
- [ ] 2.6 Update the agent `install.md` in the backend repository to show how an agent reads `al wait` events (its standard output must be read, lines can repeat so dedupe by `id`, and messages sent while it was not running arrive when it starts) and replies with `al send`; verify an agent following it can receive and answer a message

## 3. cli

- [ ] 3.1 Implement `al wait` incoming events: handle `event.deliver` requests, write the params as one compact line to standard output (`{"type": "message", "id", "text", "sent_at"}` for a message), flush, and only then respond with `result: {}`; do the write off the connection loop with a 5 second timeout; on a write error or timeout respond with `-32001` reason `not_received`, log it to standard error, and keep running (the Assistant Link stays online); keep `-32601` for other requests and ignore unknown notifications; verify with tests against a mock WebSocket server for ordering (the line is written before the acknowledgement is sent), several events in order, multi-line text, an event of an unknown `type` (still written), `--human` (standard output unchanged), a closed standard output and a full pipe nobody reads (error within about 5 seconds, still connected, the same event written once the reader resumes), and unrelated requests
- [ ] 3.2 Implement `al send <text>` and `al send -` (standard input, one trailing line feed dropped): `POST /alp/v1/messages` with the Link key, print `{"message_id", "sent_at"}` or `{"error": {"code", "message"}}` (text for `--human`), exit 0/2/3/4/5 as in the spec, never open an agent connection, send no `client_id`, and make one attempt without retrying; verify with tests against a mock HTTP server for an argument, standard input, a missing text (exit 2), no key (3), `text_too_long` and `unauthorized` (4), and an unreachable server (5); it passes the shared text test vectors to the service unchanged
- [ ] 3.3 Update `cli/README.md` with `al send`, the event format on `al wait`'s standard output (`type`, readers ignore unknown fields and types, lines can repeat, missed events arrive first), the acknowledgement timing, exit code 4's wider meaning, and that `al send` does not retry (a retry after exit 5 may duplicate the message); verify every documented command runs as written against a local service
